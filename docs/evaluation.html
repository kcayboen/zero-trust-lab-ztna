1. What was built

The model was built in a Proxmox Virtual Environment test-bed of five virtual machines: a Windows Server 2022 domain controller (DC01), an OPNsense firewall, one instructor workstation and two student workstations (Windows 11). A VLAN-aware virtual bridge separates three zones: Students (VLAN 11), Instructor (VLAN 20) and Server (VLAN 30). Only the firewall carries all three VLANs, so traffic between zones must pass it. All user accounts are synthetic; no real person’s data was used.

Helps with items: D1

2. Network zones and the enforcement point

OPNsense is the Policy Enforcement Point (PEP). Each zone has its own rules: workstations may reach only the domain services of DC01 (Kerberos, LDAP, DNS, SMB for Group Policy) and DNS; instructors may also ping student workstations; DC01 may reach workstations only for remote administration (WinRM). Everything else is denied and logged. Inside a zone, where traffic does not pass the firewall, each workstation’s Windows firewall is controlled only by Group Policy and blocks connections from other workstations.

Helps with items: C2 C6

3. Identity, roles and policy decisions

The Policy Decision Point (PDP) is Active Directory together with a policy decision script on DC01. Access is granted to role groups (students, instructors, administrators), never to individuals. Group Policy sets the logon rights: students may use any student workstation, but not the instructor workstation or the server. For each request, the script checks the user (exists, enabled, not locked, has a role), then the device (registered, domain member, MAC address matches), then the policy matrix, and returns Allow or Deny with a reason code. Anything not explicitly allowed is denied.

4. The five demonstrations

These are the demonstrations performed in the live session. Each is shown here with the screens captured when it was run on the test-bed.

Demo A A student is refused at the instructor workstation

In the live session, student01 signs in at Instructor1 with the correct password. The sign-in is refused because students do not hold the logon right on instructor workstations; the refusal is forwarded to the domain controller as event 4625.

Demo B Repeated wrong passwords lock the account

Five wrong passwords for the synthetic test account lock it; even the correct password is then refused. The domain controller records the lockout (event 4740), and the PDP returns DENY_USER_LOCKED. Lockouts expire after 15 minutes.

Demo C Lateral movement between workstations is blocked

From Student1, a connection to the domain controller’s login service succeeds, while connections to Instructor1 (another zone) and Student2 (same zone) time out. The firewall logs the cross-zone attempt; the same-zone attempt is dropped by Student2’s own firewall.

Demo D An unregistered device gets no address and no access

Student2’s network card is given an unregistered MAC address. It receives no DHCP address, and everything it sends, even from a self-assigned address, is blocked and logged. With its registered MAC it receives its reserved address again.

Demo E Security events are collected centrally

Workstation security events reach the domain controller within seconds through Windows Event Forwarding; every PDP decision is an event in the domain controller’s Application log; network decisions are in the firewall log.

5. Measured performance

Six engineering indicators were measured. Each was measured in five independent trials of 100 events; the five-trial mean was compared with the threshold set in the methodology (Table 2 of the manuscript).

IndicatorThresholdFive-trial mean
Authentication latency (end-to-end at the workstation)≤ 300 ms (mean and 95th percentile)17.6 ms (95th percentile 19.8 ms)
Policy decision latency≤ 200 ms4.36 ms
RBAC enforcement accuracy≥ 99%100%
Unauthorized authentication blocking≥ 99%100%
Micro-segmentation rule drops (cross-zone attempts)≥ 99%100%
Logging completeness (granted and denied events)100%100%
How the measurements were made.
  • Every test used a fixed list of cases prepared before the test; the expected result of each case was derived from the policy, not from the system being tested.
  • Each trial was an independent run with the order of cases shuffled; times were measured inside the virtual machines.
  • Every figure was recalculated from the raw per-event records.
  • For logging and segmentation, deliberately broken records were added as a check, and the counting reported exactly those as missing.
  • The first RBAC run scored 95%. The cause was an error in how the policy script read account attributes; it was corrected and the test repeated (two of the three refinement cycles allowed by the methodology were used).

6. What running it would involve

The model uses only software that is already available or free: Active Directory and Group Policy (Windows Server) and the open-source OPNsense firewall. Proxmox was used only for testing. The recurring administrative tasks would be:

TaskWhenWhat it involves
Onboard and offboard studentsEach termCreate or disable accounts and add them to the student group; access follows from the group
Register a workstationWhen a PC is added or its network card replacedA DHCP reservation and registered-MAC entry on the firewall, and a computer object with its MAC address in Active Directory
Change who may access whatWhen roles or policy changeEdit the role groups or the firewall rules, and keep the policy matrix and firewall consistent
Respond to lockoutsAs neededLockouts expire after 15 minutes; staff can unlock earlier from Active Directory
Review logsRoutinelyForwarded workstation events and PDP decisions on the domain controller; the firewall log on OPNsense

The skills involved are Active Directory and Group Policy administration, VLAN configuration on the switches, and OPNsense firewall administration. In the actual laboratory the VLANs would be configured on the access switches instead of a virtual bridge.

7. Limitations and changes from the plan

  • The test-bed has five virtual machines and synthetic accounts. The actual laboratory has more users and devices, and response times may be higher under real load.
  • Lateral movement was tested with TCP connection attempts only.
  • MAC addresses can be spoofed. The model also requires domain membership; port-based authentication (IEEE 802.1X) is recommended for a production deployment if the switches support it.
  • The firewall log is kept on the firewall itself; a production deployment should forward it to a central log server.
  • Changes from the original plan: Windows Server 2022 instead of 2019; reservations-only DHCP with no dynamic range; the firewall’s local log instead of a remote syslog server.
  • Defects found during testing (account-lockout auditing not enabled, workstation firewall logging inactive, the policy script error above) were corrected and are listed as recommendations in Chapter 3.
  • Moving from the test-bed to the actual laboratory would require the University’s review and approval of the new controls.
