Zero Trust Network Access for a university computer lab

A working Zero Trust model, with identity, role, device and network checks on every request. It was built on a five-VM Proxmox test-bed and measured against six engineering thresholds. It passed all six.

The problem

A shared lab is a flat network

Every PC sits on the same switching layer, so a device inside the lab is trusted by default. Students rotate each term, PCs are shared, and one compromised or borrowed machine can reach the instructor's PC and the server.

The approach

Never trust, always verify

Following NIST SP 800-207, every request is judged on who the user is, what role they hold, which device they use, and what they want to reach. Anything not explicitly allowed is denied and logged.

Design

Five machines, three zones, one enforcement point

A VLAN-aware bridge separates the Student, Instructor and Server zones at layer 2. Only the firewall carries all three VLANs, so every packet between zones has to pass the policy enforcement point.

PDP

Policy decision point

Active Directory plus a PowerShell policy engine. It checks the user (enabled, not locked, role), then the device (registered, domain member, MAC match), then a versioned policy matrix, and returns Allow or Deny with a reason code.

PEP

Policy enforcement point

OPNsense routes between the zones, with default-deny and logging per zone. Inside a zone, each Windows host firewall is controlled only by Group Policy, which stops same-VLAN lateral movement.

RBAC

Role-based access

Access goes to role groups, never to people. Group Policy logon rights keep students off instructor PCs and the server, while any student may use any student PC.

Devices

Device validation

Reservation-only DHCP gives unknown MACs no address, a registered-MAC firewall gate blocks and logs them, and domain membership is required as well.

Monitoring

Continuous monitoring

Windows Event Forwarding sends workstation events to the domain controller. Every PDP decision is an event, and every firewall denial is logged.

Safety

Safe to iterate

The VMs were snapshotted before every configuration change, all accounts are synthetic, and the test-bed is isolated from production.

Measurement rigor

Making 100% mean something

A test that grades itself always passes. These safeguards keep the results honest.

  1. Answers fixed before the testEach scenario used a case file written in advance. The expected decisions were derived from the policy document, not from the system being measured.
  2. Independent trialsEach trial ran as a fresh process with the case order shuffled and times measured inside the VMs.
  3. Recomputed from raw recordsEvery table was rebuilt from the per-event logs, never from the test scripts' own summaries.
  4. Independent evidenceFirewall logs, forwarded Windows events and host firewall logs were matched on exact keys (source port, user, case ID) within time windows.
  5. Negative controlsRecords were deliberately broken, and the counters reported exactly those as missing, which proves they can fail.
  6. Cache checkThe domain controller logged exactly one Kerberos request per measured logon, so no result came from cached credentials.
Debugging story

From 95% to 100%

The first RBAC run scored 95%: every request that originated from the domain controller was denied.

The cause was reading .Value on an AD ResultPropertyValueCollection, which silently returned nothing. The account flags looked like 0, and that also hid disabled and locked accounts from the policy engine.

The fix was unit-tested on the failing cases before the whole cycle was re-run. The accuracy reached 100%, using two of the three refinement cycles the method allowed.

Also found and fixed

Gaps that tests exposed

  • Lockout and unlock events were not audited; User Account Management auditing was added.
  • Host-firewall drop logging was never active: the policy was written to the wrong key, and the log folder was missing on the image.
  • A clock mismatch between the test host and the lab was removed by timing everything on the domain controller.

Each fix was made under a VM snapshot, verified, and turned into a recommendation for a production rollout.

Limits

What the numbers do not show

  • Five VMs and synthetic users: latency may rise under real lab load.
  • Lateral movement was tested with TCP connection attempts only.
  • A MAC gate can be fooled by spoofing. Domain membership is the second check, and IEEE 802.1X is the production recommendation.
